# ADR-003: การเลือกใช้ Hybrid LLM Provider ร่วมกับ Rule-based Fallback Chain สำหรับ AI Assistant

* **สถานะ**: อนุมัติแล้ว (Accepted)
* **วันที่ตัดสินใจ**: สัปดาห์ที่ 6
* **ผู้มีส่วนร่วมในการตัดสินใจ**: นายสุรวัจน์ ชลเรืองทรัพย์ (AI Engineer), นายสรวิชญ์ มีมาก (QA Lead)
* **บริบทและปัญหา (Context)**: ระบบต้องการเพิ่มฟีเจอร์ AI ในการช่วยแนะนำหนังสือแก่นักอ่านตามภาษาธรรมชาติ (Semantic Search & Intent Matching) ทว่าในสภาพแวดล้อมจริง บริการภายนอกของ LLM อาจเกิดปัญหาความหน่วง (Latency), โควตาหมด (Rate Limit Exceeded), หรือการหยุดชะงักของเครือข่าย

---

## การตัดสินใจ (Decision)
ทีมตัดสินใจนำ **Hybrid AI Architecture** มาประยุกต์ใช้:
1. ใช้ **Google Gemini API** เป็นโมเดลหลักเนื่องจากมี Free Tier และเข้าใจภาษาไทยได้ดี
2. กำหนด Timeout ในการเรียก AI ไว้ที่ 3,000 มิลลิวินาที
3. ออกแบบ **Graceful Fallback Chain** ด้วย Rule-based SQL Query แนะนำหนังสือยอดนิยมตามหมวดหมู่ทันทีเมื่อเกิดเหตุขัดข้อง เพื่อไม่ให้ระบบล่ม

---

## ทางเลือกอื่นที่พิจารณา (Alternatives Considered)

1. **OpenAI GPT-4o API ล้วนโดยไม่มี Fallback**:
   * *ข้อดี*: คุณภาพคำตอบสูง
   * *เหตุผลที่ไม่เลือก*: มีค่าใช้จ่ายต่อ Token (ขัดแย้งกับ NFR Cost Ceiling = $0) และหากเกิดเหตุการณ์ API ล่ม ผู้ใช้จะเห็นหน้าจอข้อผิดพลาด 500 ทันที
2. **On-device Small LLM (เช่น Ollama WebAssembly)**:
   * *ข้อดี*: ทำงานได้แม้ Offline
   * *เหตุผลที่ไม่เลือก*: ขนาดโมเดลหลายกิกะไบต์ทำให้การโหลดหน้าเว็บช้ามาก และกินแรมเครื่องผู้ใช้สูงเกินไป

---

## ผลลัพธ์และการประเมิน (Consequences)

* **ผลเชิงบวก**:
  * ระบบมี High Availability 100% แม้ไม่มีอินเทอร์เน็ตเชื่อมต่อกับ Google AI
  * ต้นทุนการใช้งานคงที่อยู่ที่ $0.00
  * มีการแจ้งเตือนผู้ใช้อย่างโปร่งใสว่าเป็นผลลัพธ์จาก AI หรือระบบสำรอง
* **ผลเชิงลบและความเสี่ยง**:
  * ผลลัพธ์ในโหมด Fallback มีความฉลาดน้อยกว่าโหมด AI เต็มรูปแบบ (ยอมรับได้เนื่องจากเป็นระบบสำรองชั่วคราว)
